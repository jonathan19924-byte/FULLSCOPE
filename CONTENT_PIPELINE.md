# Content Pipeline — Design Notes

*This is a working design/rationale document for FullScope's content-generation pipeline — separate from `PRD.md`, which describes what's built. `PRD.md` answers "what does the app do"; this answers "why does the pipeline work this way, what tradeoffs did we make, and what's still unresolved." Meant to be updated every time we touch content generation, so a future session (or a future you) doesn't have to re-derive reasoning that already happened once.*

*Last updated: 2026-07-31.*

---

## 1. Core editorial philosophy

Everything else in this document is downstream of a small number of hard rules. When in doubt about a future change, check it against these first.

1. **A story needs 2+ independent sources before it exists at all.** Enforced at clustering (`buildClusteringPrompt`) — a cluster with fewer than 2 distinct-source articles is dropped before it ever reaches generation. This is a corroboration bar, not an editorial-fit bar (see #2).
2. **A story needs a genuine two-sided dispute, not just corroboration — and "dispute" is topic-agnostic, not implicitly political.** Added 2026-07-29 (see §5, Decision Log). Two outlets reporting the same arrest doesn't mean there are "two sides" to the arrest. This is a *separate* gate from #1 — a story can pass the source-count bar and still fail this one. The first version of this gate's prompt wording used only political/security examples (a policy debate, a contested use of force), which risked biasing the model toward treating "genuine dispute" as inherently political — fixed 2026-07-30 to explicitly include business (contested layoffs, activist-investor fights), sports (disputed calls, doping accusations), entertainment, science/tech, and legal disputes as equally eligible, with parallel "routine, no dispute" examples for each domain (a plain earnings report, an uncontested final score) so the negative case is topic-balanced too.
3. **Perspectives are named by the argument, not the tribe making it.** "Security-first response" vs. "restraint and de-escalation," never "the right" vs. "the left," a party name, or a demographic label. This is the actual neutrality mechanism — a group label is inherently more loaded than an argument label, and inconsistent naming (one side by argument, one by identity) reads as biased even when the underlying content isn't.
4. **The perspective axis is locale-aware AND topic-agnostic, not a fixed template.** English-mode prompts still default to left/progressive vs. right/conservative (a reasonable fit for US *political* news specifically). Hebrew mode explicitly does *not* force that — it lets the model pick whichever real axis divides people on *this* story, and that axis doesn't have to be political at all: security vs. rights, religious vs. secular, coalition vs. opposition (politics); management vs. labor, growth vs. fiscal caution (business); tradition vs. reform, fairness vs. commercial interest (sports); or whatever real divide fits a legal, scientific, or cultural story. Same 2026-07-30 fix as rule #2 above — the example list was originally all-political, which risked the same bias here as in the dispute gate.
5. **Stories are living, not static.** New coverage that's a development of an existing story gets folded into it (timeline entry, merged sources, possible revival from archive) instead of spawning a duplicate. A reader-trend needs 2+ *distinct* users independently making the same point before it's folded in — never a single opinion, no matter how many times one person repeats it.
6. **Moderation is for abuse, not disagreement.** The moderation pass hides harassment, threats, doxxing, spam — explicitly never a strongly-worded opinion or a one-sided take. That's supposed to happen here; suppressing it would defeat the point of the community layer.
7. **When a pipeline judgment call is uncertain, default to the less destructive option.** The coverage-merge check defaults to "new story" rather than "fold into existing" on any doubt — an incorrect merge corrupts a real story's content, while an incorrect "new" just creates an extra story the existing dedup pass can still catch later. Same asymmetry logic should apply to future judgment calls added to the pipeline.

## 2. Pipeline stages, in order, with the reasoning behind each

### Stage 1 — Fetch (`src/lib/rss/fetch-rss.ts`)
Pulls RSS from 19 curated Hebrew/Israeli sources (or ~31 English sources in English mode) into `raw_articles`, tagged with a `source_lean` for later use.

**As of 2026-07-31, runs every 3 hours as the first step of the same GitHub Actions job as Stage 2**, not a separate daily Vercel cron. Two concrete reasons motivated moving it: (1) a once-daily fetch meant Stage 2's 3-hourly cadence was mostly wasted for freshness — new raw content only entered the system once a day regardless of how often processing ran, so a story breaking after that day's fetch wouldn't be visible until the next day's. (2) most publisher RSS feeds only expose their most recent N items (commonly 20-50) — a high-volume source can cycle through that window in a few hours, so a once-daily check risks silently *missing* articles that scrolled off the feed, not just processing them late. `fetch-rss` makes no Claude API calls, so running it 8x/day instead of 1x/day costs essentially nothing extra.

**Source list curation (2026-07-31)**: trimmed from ~33 to 19 sources. Cursorinfo was dropped for publishing in **Russian, not Hebrew** — a real fit problem, not just volume noise, since cross-language topic matching during clustering is inherently less reliable. The left/right split was deliberately kept at 4-and-4 (Davar, Local Call, Kol Ha'ir, Shakuf vs. Israel National News, Srugim, Kipa, Israel Defense) rather than trimming left-leaning sources down to one, specifically because Srugim and Kipa are the two highest-volume sources in the whole list — cutting left-leaning coverage further while keeping those would have skewed the input pool itself before any generation happens, which matters directly for an app whose premise is genuine two-sided coverage. Kore was kept despite being very high-volume (its content checked out as legitimate Hebrew news, not noise) — the per-source cap below is what actually solves its volume problem, not removal.

**Telegram added as a second raw source (2026-07-31, `src/lib/rss/fetch-telegram.ts`)**: 8 channels, fetched from each channel's public `t.me/s/<handle>` preview page (no bot/account auth needed) and written into the same `raw_articles` table with a new `source_type` column (`'rss'` vs `'telegram'`) so the backend can tell them apart — nothing downstream (clustering, dispute gate, generation) treats them differently. All 8 handles were live-verified before being added (confirmed real, active, currently posting) — see Decision Log for the full list and verification method. Every Telegram row gets `source_lean: 'unclassified'` rather than a guessed bucket — assigning real lean labels requires reading enough actual content first, deliberately deferred rather than repeating the mistake of guessing (see the bias-audit Decision Log entry above). Telegram channel names are included in `ACTIVE_SOURCE_NAMES` (Hebrew mode only) so the same per-source cap applies to them.

### Stage 2 — Cluster (`buildClusteringPrompt` in `process-articles.ts`)
Groups same-event articles by topic. Two gates happen here, in order:
1. **Source-count gate**: drop any cluster with fewer than 2 distinct-source articles (rule #1 above).
2. **Genuine-dispute gate** (added 2026-07-29): drop any cluster that's a routine incident report — an arrest, a traffic accident, someone hospitalized, a missing-person case, a routine indictment — where there's a clear outcome and no real controversy. Rejected clusters have their source articles marked `processed` immediately (same as the source-count rejection path) so they aren't reconsidered — and rejected again — every subsequent run.

Both gates are boolean judgment calls made by the same clustering prompt call (no extra API cost) — see §4 for the exact wording and §5 for why this was added.

Clusters are then ranked and capped at `MAX_CLUSTERS_PER_RUN` (currently 10) so a single run's duration stays predictable regardless of backlog size — see the 2026-07-28 timeout incident in the git history (`cabda00`, `23d58ea`) for why this cap exists. Anything cut off by the cap just rolls into the next run (every 3 hours), since rejected/uncapped articles simply stay `processed: false`.

**Input selection (`fetchUnprocessedArticles`, 2026-07-31)** — capped **per source** (`MAX_ARTICLES_PER_SOURCE_PER_PASS`, 10), not by a single global limit. The previous global-limit approach (most-recent 150 across all sources combined) let high-volume sources crowd out everything else — observed directly in production: with a 150 global cap, Kore alone filled 45% of the slots and 17 of 33 active sources had zero representation in the window at all. A per-source cap guarantees every active source gets a fair shot each run regardless of how prolific any one of them is. Implemented as one small query per source run in parallel (`Promise.all`), not a single query with a group-by-limit, since Supabase's query builder doesn't support per-group limits natively and the source list is small enough that N queries is simpler than a raw SQL/RPC alternative.

**Ranking (`clusterRankKey`, 2026-07-30)** — lexicographic, in priority order: (1) distinct source count (true corroboration breadth, not raw article count — several articles from the same outlet republishing shouldn't outrank a story 3 genuinely different outlets are covering), (2) `dispute_intensity` (1-5, from the same clustering call, no extra cost — how significant the disagreement actually is, not just whether one exists), (3) total article text volume, computed locally from the already-fetched rows rather than asked of the model — a cheap proxy for how substantively a story has actually been reported on. The clustering prompt is also asked directly to return at most `MAX_CLUSTERS_PER_RUN` clusters (see the truncation incident below) — the sort/slice here is verification of that, not the only thing enforcing it.

**Incident, 2026-07-30**: a 2000+ article backlog made Claude enumerate enough clusters that the JSON response exceeded the clustering call's `max_tokens` and got truncated mid-string, silently discarding the entire clustering pass (parse error caught, `clusters = []`, zero new stories, the dispute gate never even exercised). First attempted fix — raising `max_tokens` 4000 → 8000 — did *not* work; it just moved the truncation point further out (confirmed by observation: position 8826 → 17377), proving response size scales with backlog size, not a fixed constant. The actual fix has two parts: (a) capped the *input* to `MAX_ARTICLES_PER_CLUSTERING_PASS` (150, most-recent-first) so the candidate pool per run is bounded, and (b) asked the prompt directly for at most `MAX_CLUSTERS_PER_RUN` clusters rather than enumerating everything it can find — (b) is the real structural fix, since it bounds the model's own output regardless of how large the input pool is; (a) is still kept as a secondary bound on prompt cost/latency. Lesson for next time: if a clustering/generation response is truncating on a large backlog, check whether the fix needs to bound *output* (ask for fewer things) rather than just raising `max_tokens` or trimming input — those don't fix output size that scales with backlog content, only output size that scales with backlog *volume sent in*.

### Stage 3 — Coverage-update check (`findRelatedStory` / `applyCoverageUpdate`)
Before generating a *new* story for a cluster, check whether it's actually a development of an existing story (live or archived). If so: append a timeline entry, merge in new sources, extend `published_at`, revive from archive if needed, log a `coverage`-type `story_updates` entry — no new story row. Biased toward "new" on any doubt (rule #7). Candidates (top 8) come from a pgvector similarity search (`match_stories`, 2026-08-13, see Decision Log) across ALL live + archived stories — no category filter, since similarity narrows better than category did and doesn't share category's blind spot when a story was mis-classified. Falls back to the original recency-windowed, category-scoped query (10 live + 5 archived) if the embedding call or the similarity RPC fails for any reason.

### Stage 4 — Story + post generation (`buildStoryPrompt`, `buildPostsPrompt`)
Only reached if a cluster passed both clustering gates and wasn't claimed by the coverage-update check. Generates: title, summary, what-happened, timeline, two named perspectives (rules #3, #4), why-they-differ, sources, image keywords (always English, since Pexels' index doesn't understand Hebrew — see the bathroom-photo incident in the git history that motivated this), then 10 reaction posts split unevenly across the two perspectives.

**Cross-field repetition (fixed 2026-07-31, see Decision Log)**: this prompt asks for 9 output fields (`summary`, `what_happened`, `what_happened_timeline`, both perspectives' summaries and claims, `key_differences_cause`/`impact`) that all render on the same story page. The original prompt described each field's length/tone in isolation, with no instruction that they'd appear together — so the model defaulted to rephrasing the same 2-3 core facts across all of them (users reported this directly: summary restated in what_happened, restated again in the timeline, perspective claims just re-splitting their own summary sentence). The fix added one explicit block to `buildStoryPrompt` giving each field a distinct job and stating outright that duplicating another field's content is a defect — not a schema change, same single Claude call. Verified against a real live cluster (a Lebanon/Iran escalation story) post-fix: timeline entries surfaced facts (unit numbers, locations) not mentioned in `what_happened`; perspective claims were concrete assertions distinct from their own summary paragraph, not that paragraph split into bullets.

### Stage 5 — Moderation (`moderateNewPosts`)
Runs before trend detection (so a flagged post can't get folded into a story in the same pass). Batches 25 unmoderated `community_posts` through Claude, hides genuine policy violations (rule #6), emails an alert either way.

### Stage 6 — Trend detection (`checkStoryTrends` / `applyTrend`)
Groups uncredited, non-hidden community posts by related story; only considers a story if ≥2 *distinct* `user_id`s made posts about it (re-verified server-side, not trusted from the prompt — rule #5). Folds the point into a claim or the why-they-differ text, credits the contributing posts, logs a `trend`-type `story_updates` entry.

### Stage 7 — Dedup (`dedupeStories`)
Runs every invocation regardless of whether new stories were generated, since duplicates can exist from past runs. Compares all *live* stories against each other for same-real-world-event duplicates (distinct from the coverage-update check, which compares *new* coverage against the existing body — see the code comment on `buildRelatedStoryPrompt` for the exact distinction). Archives (not deletes) the losing duplicates, keeping the most-recently-generated one as the survivor, logs a `merge`-type `story_updates` entry.

### Stage 8 — Cap enforcement + archiving
Hard backstop trimming the live story count to `MAX_STORIES` (60) if anything pushed it over. Archives rather than deletes (2026-07-29, `a606fb4`) — posts, likes, and reader contributions all stay intact, and an archived story can be revived by Stage 3 if new coverage on it shows up later.

### Stage 9 — Image backfill (`backfillMissingImages`)
Best-effort, runs concurrently (parallelized 2026-07-28 after it was found to be a real contributor to a pipeline timeout — see `cabda00`). Derives English image keywords via a small Claude call, searches Pexels, falls back to a category icon if nothing's found — never blocks story generation.

**Photo selection now vets each candidate before accepting it (added 2026-07-31, see Decision Log)**: `findStoryImage` (`src/lib/articles/pexels.ts`) fetches up to 5 Pexels candidates instead of 1, skips any URL already assigned to another live story (free — no API call), and sends the current candidate's actual image bytes to Claude (`callClaudeVision`) asking whether it contains a legible sign, banner, placard, or other readable text. Only escalates to the next candidate if the current one is a duplicate or fails that check; falls back to a category-level search with the same logic if every title candidate fails, then to the existing icon placeholder. Typical cost is 0-1 vision calls per story (most stock photos have no signage at all); worst case is bounded by the 5-candidate cap per search.

## 3. The two distinct "is this the same story" checks — don't conflate them

There are two separate mechanisms in this pipeline that both ask some version of "is this the same as something else," and it's easy to confuse them:

| | Coverage-update check (Stage 3) | Dedup check (Stage 7) |
|---|---|---|
| Compares | New cluster vs. existing stories (live + archived) | Live stories vs. each other |
| Runs | Once per new cluster, before generation | Once per invocation, over everything |
| Answers | "Is this new reporting a development of an existing story?" | "Did we accidentally generate two stories for the same event?" |
| On match | Folds into existing story, no new row | Archives the newer/duplicate, keeps one survivor |
| Logged as | `story_updates` type `coverage` | `story_updates` type `merge` |

They're complementary, not redundant: the coverage-update check prevents *new* duplicates from being created; dedup cleans up duplicates that slip through anyway (e.g., two clusters from the same run that were similar enough to both look "new" but weren't caught by the coverage check against each other, since it only checks against stories that already exist in the DB, not sibling clusters from the same batch).

## 4. Key prompt design decisions (exact current wording lives in `process-articles.ts`)

- **Stance-based perspective naming** (rule #3) is enforced with an explicit instruction (`nameNeutrality` in `buildStoryPrompt`) requiring both sides be phrased with the same register and specificity, precisely because an asymmetric mix (one side named by argument, one by identity) was identified as reading as biased even when the content wasn't.
- **Locale-aware axis selection** (rule #4): the Hebrew-mode prompt explicitly lists example axes (security-first vs. rights-first, religious vs. secular, coalition vs. opposition, hawkish vs. dovish) as *illustrative, not exhaustive* — the instruction is "pick whatever genuinely fits," not "pick from this list."
- **The genuine-dispute gate** (added 2026-07-29, rule #2) is phrased as a binary classification with explicit positive and negative examples in the prompt itself (policy debate / contested decision / controversial use of force / disputed ruling vs. arrest / traffic accident / hospitalization / missing-person case / routine indictment) rather than an abstract instruction — concrete examples were chosen because "is this controversial" is a fuzzier judgment than "are there 2 sources," and under-specifying it risked either over-filtering (rejecting real disputes that happen to involve police/courts) or under-filtering (the original problem).
- **Image keywords are always requested in English**, regardless of locale, because Pexels' search index doesn't meaningfully understand Hebrew — this was learned the hard way (a Hebrew-language search for a legal-ruling story returned an unrelated bathroom photo).

(C) a blinded second Claude call (shown only "Perspective 1"/"Perspective 2", no labels, order randomized) judging language-level neutrality — flagged 7 of 8 sampled stories for asymmetric confidence (one side's claims stated as settled fact, the other's hedged/attributed to "critics"). **Fixed (B)**: added `randomizePerspectiveSlots` — a post-generation coin flip (Hebrew mode only) that swaps perspective_a/b's name+summary+claims together as a unit, so which real-world stance lands in the more-prominent "A" slot (confirmed via `perspectives.tsx`: A renders first) is mechanically ~50/50 regardless of Claude's own tendency to list the establishment view first. Verified with 5,000 synthetic calls: 49.0%/51.0% split, fields always swap as a consistent unit, never partially. **Attempted but did not fix (C)**: added an explicit "epistemic parity" instruction to `buildStoryPrompt` asking both perspectives' claims to be stated with matching confidence/hedging. Re-tested against 10 freshly generated real stories post-fix — the blinded judge still flagged 7/7 successfully-judged stories (same or worse than the 87.5% baseline). See Open Problems below — this needs a different approach, not shipped as "fixed."
- **2026-07-31** — Fixed cross-field repetition in story generation (`buildStoryPrompt`). Motivated by direct user reports that stories often say the same thing in `summary`, then again in `what_happened`, then again in the timeline, and that perspective "claims" often just restated the perspective's own summary sentence. Root cause: 9 output fields asked for in one prompt, each described in isolation (length/tone only), with no instruction that they'd all render on the same page — the model defaulted to rephrasing the same 2-3 core facts across all of them. Fix was prompt-only (no schema/cost change): added an explicit block giving each field a distinct job (headline takeaway vs. mechanical facts vs. sequential timeline vs. narrative reasoning vs. concrete claims vs. why-they-disagree) and stating that duplicating another field is a defect. Verified against a real live cluster post-fix — timeline surfaced facts absent from `what_happened`, perspective claims read as genuinely separate from their own summary paragraphs. Closes the `summary`/`what_happened` overlap noted in the 2026-07-29 open-problems entry (Stage 4) — that entry is now removed since the underlying cause is fixed, not just the display symptom.
- **2026-07-31** — Photo selection now rejects candidates containing legible signs/banners/text (via a real Claude vision check on the image itself, not a keyword filter on Pexels' text description) and skips images already used by another live story. Motivated directly by a production case: a live story about a Netanyahu-Trump meeting on Iran carried a Pexels stock photo of a protest sign reading "TRUMP, NETANYAHU = WAR CRIMINALS" — a photo visually taking a side on an already-contested topic, which no amount of matching against the platform's own "no bias" story-generation rules would have caught, since the bias was in the image, not the text. An initial proposal to keyword-filter Pexels' `alt` text (banning words like "protest," "banner," "slogan") was explicitly rejected as the wrong mechanism — it only catches cases where Pexels' own description happens to use a flagged word, not the actual problem of a legible claim printed in the photo itself. The shipped fix inspects the candidate image directly instead. The one specific story already carrying that photo was hand-corrected (its `image_url` swapped for a new clean pick via the same code path) — found to already be archived off the live feed by the story cap, but fixed anyway in case its page is ever reached directly.
- **2026-07-31** — Moved `fetch-rss` from a daily Vercel cron to every 3 hours as the first step of the same GitHub Actions job as `process-articles`; trimmed the source list from ~33 to 19 (dropped Cursorinfo for being Russian-language, kept the left/right split at 4-and-4 rather than letting it skew toward the two highest-volume sources both being right-leaning); switched article selection from a global 150-article limit to a per-source cap of 10. Motivated by a real conversation working through the actual tradeoffs rather than guessing: checking is cheap (no Claude cost) so frequency should be driven by freshness/resilience to missed cron fires, not cost; a global recency-ordered limit measurably let one source dominate (Kore was 45% of the window, 17 of 33 sources had zero representation); and daily-only fetching meant the 3-hourly processing cadence wasn't actually improving freshness at all, since no new raw content entered the system between daily fetches.

- **2026-07-30** — Broadened the dispute gate and perspective-axis examples (rules #2, #4) to explicitly cover business, sports, entertainment, science/tech, and legal disputes, not just political/security ones. Motivated directly by observing that the first production run of the dispute gate only ever generated political/security stories (Israel-Qatar relations, Iran-Israel tension, reserve-duty economics, a media-incitement controversy) even against a backlog that included business and sports topics — the original prompt wording's examples were 100% political, which plausibly primed the model to under-recognize non-political disputes as genuine. Verified the fix with 4 controlled test cases (a labor-dispute strike, a routine earnings report, a disputed referee call, a routine final score) spanning business and sports — all 4 classified correctly post-fix. Also flagged, not yet acted on: the `category` field itself is still hardcoded to `Politics|World|Technology|Science` — no Business or Sports category exists, so a genuine business/sports dispute currently gets filed under whichever of these 4 fits loosest (usually "World"). Worth a deliberate decision later, not fixed as part of this change since it ripples into the DB check constraint, category chips, and i18n.
- **2026-07-30** — Rank clusters by distinct source count, then dispute intensity (new 1-5 rating), then local article-text volume, instead of raw article count. Also had the clustering prompt itself cap its own output at `MAX_CLUSTERS_PER_RUN` directly, after discovering (see Stage 2 incident writeup) that raising `max_tokens` alone doesn't fix truncation on a large backlog — only bounding the model's own output does.
- **2026-07-30** — Verified the 2026-07-29 genuine-dispute gate against real production data for the first time: 16 routine clusters correctly rejected (a weekly religion column, driver-error/car-maintenance tips, phone tips, cost-of-living, real-estate slowdown, bird migration, "surprising animal video," etc.), 1 genuine political dispute correctly generated. First live confirmation the gate works as intended, not just on synthetic test cases.
- **2026-07-29** — Added the genuine-dispute gate at clustering (rule #2). Motivated by direct observation of the live feed: routine crime-blotter stories (a body found, a theft arrest, a missing-person case, a snake bite hospitalization) were being forced into the two-perspective format with no real dispute to represent, producing thin or manufactured-feeling "sides." The fix is at the clustering stage rather than the generation stage, so a routine report never reaches story generation at all instead of generation trying (and failing) to invent a dispute.
- **2026-07-29** (`a606fb4`, `00b432f`) — Stories removed from the feed are archived, not deleted; new coverage can revive an archived story instead of only ever creating new ones. Motivated by wanting evicted/merged stories to not just vanish, and by the observation that "this is actually the same ongoing situation, just interrupted" is a real, common case (see the Iran/Hormuz and garbage-truck-fire test cases used to verify this).

## 6. Open problems / things to watch (living list — update as found, don't let this go stale)

- **Claim-level confidence asymmetry between perspectives — TWO prompt fixes attempted (2026-07-31), neither worked; needs a structurally different approach.** A blinded neutrality judge (see Decision Log) has now found this in 7/8 live stories, then 7/7 after an abstract "equal confidence" instruction, then 8/8 after replacing that with a mechanical fixed-attribution-template instruction — no improvement across either attempt, regardless of which real-world side was favored (not a fixed left/right tilt; flips direction story to story). Reading the actual flagged evidence from the second attempt: the asymmetry isn't in attribution grammar (both sides now use identical "[Perspective] argues that..." framing) — it's in word choice and specificity one level below that. One side reliably gets vivid, concrete, confident detail (named figures, exact numbers, declarative claims) while the other gets abstract, generic, hedged phrasing, and a fixed sentence template doesn't touch that. **Next step (deferred, not yet built)**: a post-generation detection/rewrite pass, reusing the same blinded-judge mechanism that's now reliably caught this exact problem three separate times — run it as a real pipeline stage after each story generates, and have Claude specifically rewrite whichever side's claims got flagged as more hedged/abstract, then re-check. Prompt-only fixes at the sentence level look exhausted; this needs to be caught and corrected after the fact, not prevented in one shot.
- **The genuine-dispute gate is a single, unaudited boolean judgment call.** No second opinion, no logging of *why* a cluster was rejected beyond the topic name in a console log (not persisted anywhere queryable). If false negatives (real disputes wrongly marked routine) or false positives (manufactured disputes still slipping through) turn out to be common, we won't have data to diagnose it from — only anecdotal spot-checks like the one that motivated this fix. Worth considering: persisting rejected clusters somewhere queryable (even just a log table) if this needs tuning later.
- **Other categories of stories that might not fit the two-sided format**: business/sports disputes vs. routine reports were spot-checked 2026-07-30 (4 synthetic cases, all correct) — weather reports, obituaries, and market-close summaries with no controversy attached have not been specifically tested yet, though the gate's logic should generalize to them the same way.
- **No "Sports" category exists** (resolved for Business — see 2026-08-02 Decision Log entry, taxonomy now 9 categories including "Business & Economy"). Sports wasn't added since none of the 158 real stories reviewed for that expansion were sports content — worth adding if that changes, not before.
- **The coverage-update and dedup checks don't talk to each other within a single run** — a coverage-update match is checked against existing DB stories only, not against sibling clusters being generated in the same batch. Two similar clusters from the same run could both look "new" to the coverage check (nothing to compare against yet) and only get caught by dedup afterward. This is probably fine in practice (dedup is the safety net and runs every invocation) but worth knowing if a duplicate slips through inside a single run.
- **No automated eval/regression suite for prompt changes.** Every prompt change in this pipeline (including the dispute gate above) has been verified by hand — real synthetic test cases, real API calls, manual inspection of the output — rather than an automated test that could be re-run after future prompt tweaks to catch regressions. Worth considering if prompt iteration speeds up.
